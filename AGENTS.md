## Working with multiple agents

This repository may be edited concurrently by several agents, sometimes in the same working tree. Treat the working tree as shared mutable state:

- Before editing, run `git status --short` and inspect the current diff for every file you intend to touch. Pre-existing changes belong to another agent unless ownership is explicit; preserve them and do not “clean up” or revert them.
- Start with a bounded task and a small owned path set. Prefer separate areas, systems, or manifests per agent. If the task requires a file another agent is changing, re-read it immediately before patching, make the smallest compatible edit, and call out the overlap in the handoff.
- Use `apply_patch` or an equally narrow edit. Do not replace whole files, run broad formatters, or regenerate unrelated assets. Never use `git reset`, `git checkout`, `git clean`, `git stash`, or destructive deletion to resolve an overlap.
- Do not assume that an uncommitted diff, a clean status, or the latest `SESSION_HANDOFF.md` proves what another agent is doing. If ownership is ambiguous and the change could conflict, stop that part and leave a concise note for coordination rather than overwriting it.
- Keep shared coordination files low-churn. Update `docs/SESSION_HANDOFF.md` only for durable project state, and make a minimal, additive edit that records the agent's scope, changed paths, exact checks, observed results, remaining uncertainty, and next bounded task. Re-read it before updating because another agent may have changed it.
- Treat `package.json`, `package-lock.json`, central entry points, global coordinate code, and generated/output directories as high-contention paths. Change them only when necessary, own the complete related change, and mention the dependency or generated-file impact.
- Do not edit generated `dist/` output by hand. For `public/data/` or other generated files, change the source and generator, then run the appropriate sync; inspect the diff so another agent's generated output is not silently replaced.
- If committing is part of the workflow, stage explicit files from your owned scope rather than `git add -A`, and inspect the staged diff before committing. Do not amend, squash, or rewrite another agent's commit.
- Concurrent visual QA must use separate browser/server ports. The default `npm run dev` server owns port 5173; run the sync step and a Vite server on a free port for additional agents, and do not kill another agent's server.
- Validation is about the resulting shared tree, not just an agent's intent. Run targeted checks for the owned scope, then the required `npm run audit:areas` and `npm run build` before handoff when possible. Report exact commands, failures, and whether unrelated concurrent changes were present; do not claim a clean pass if the result includes an unreviewed agent's work.

## Efficient verification

- Use the command line first for code inspection, data checks, type checks, area audits, builds, and runtime logs. Documentation, metadata, and other changes with no visual or navigation effect do not need a browser check.
- For behavior that needs a running game, prefer a targeted automated probe and inspect its assertions and console output. Open the game for visual inspection only when appearance, camera behavior, walking, or navigation changed, or when a probe cannot answer the question.
- For visual or navigation changes, inspect the actual game at one relevant street-level view and one aerial view as required below. Keep this to the changed area and specific regression risk; reuse an existing game tab and server when practical.
- Capture a screenshot only when it is needed to compare a visual result or preserve evidence for a concrete issue. Capture the game viewport rather than the desktop or unrelated windows. Avoid repeated screenshots when logs, DOM state, or one focused view answers the question.

## What exists

- A working Three.js Union Square slice, derived from PhiloLabs' MIT-licensed Fable51 project, plus a coarse streamed SF city base in `src/world/CityBase.ts`. The detailed slice still has separate legacy ownership and citywide navigation/traffic are not implemented.
- Runtime geography is in `src/data/recon/`; `tools/geo/sync_data.mjs` copies a trimmed subset into `public/data/` during dev/build.
- Coarse city geography is generated by `tools/geo/build_city.py` into `public/data/city/` from a dated OSM extract and USGS raster. See `docs/CITY_BASE.md`; raw source downloads are not checked in.
- Procedural building massing and façades: `src/world/Buildings.ts`, `src/world/facade/`, `src/data/facades/`. Unique Apple/Nintendo interiors: `src/interiors/`.
- Offline Blender asset generators: `tools/bpl/`. Generated local GLBs: `public/assets/models/`.
- Current controls and entry point: `src/main.ts`. Walking/collision: `src/player/`. Pedestrians and traffic: `src/life/`.

## Guardrails

- Preserve the user's no-billed-map-service requirement. Prefer locally bundled, openly licensed data and assets. Do not add a runtime dependency on Google/Cesium/Mapbox/other metered tiles or imagery without a new user decision.
- Respect upstream MIT attribution, OpenStreetMap ODbL attribution and share-alike obligations for derived data, DataSF dataset terms, and individual asset licences. Record every new source in the relevant area manifest. Do not redistribute proprietary map meshes, street-view imagery, or interior photos.
- Do not describe an inferred façade or interior as surveyed fact. Attach source URLs, observation dates, and confidence; leave unverifiable tenants neutral.
- Keep the current game runnable while introducing tiles. New area manifests are planning/validation metadata only until a runtime loader actually consumes them.
- Avoid committing bulk raw downloads, caches, or screenshots unless there is a clear reproducibility reason and licence review.

## Before handing off changes

Run `npm run audit:areas` and `npm run build`. For visual or navigation changes, open the real game and check at least one street-level and one aerial view in the changed area; compare with appropriately licensed references when claiming fidelity. Screenshots are optional unless needed to document a visual finding. Update `docs/SESSION_HANDOFF.md` with what changed, what was verified, and the next concrete task. Do not claim citywide coverage from a successful build alone.
